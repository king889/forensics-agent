# 架构

> v2：去掉容器层，Pi 直接在 WSL 里跑。全文约 150 行。

## 1. 一句话

> 一个只读的检材目录，加上一套「按类型查命令」的技能，让模型**快速**做出有据可查的答案。

## 2. 只有四层

```
┌─────────────────────────────────────────────────────────┐
│ Pi（宿主机）                                             │
│   内置 bash / read / write / edit / rg / 网络            │
│   + skills/ 里 6 个技能（按检材类型加载具体命令）          │
│   + prompts/agent.md（行为规约）                          │
└───────────────────────┬─────────────────────────────────┘
                        │ 直接执行，无中间层
                        ▼
┌─────────────────────────────────────────────────────────┐
│ 宿主机工具（WSL 里的 apt 包）                             │
│   sleuthkit · tshark · 7z · exiftool · sqlite3 · yara    │
│   binwalk · steghide · zsteg · imagemagick ...           │
└───────────────────────┬─────────────────────────────────┘
                        │ 只读打开
                        ▼
┌─────────────────────────────────────────────────────────┐
│ case 目录                                                │
│   evi/   原始检材（约定只读，无技术强制）                  │
│   work/  中间产物                                         │
│   meta/  question.md notes.md findings.md answers.md      │
│          evidence.db                                      │
└───────────────────────┬─────────────────────────────────┘
                        │ fcase 写入
                        ▼
┌─────────────────────────────────────────────────────────┐
│ 记录层 fcase（300 行 python，只用 stdlib）                │
│   ls / hash / note / answer / status / render            │
└─────────────────────────────────────────────────────────┘
```

四层里只有最后一层是代码，其余三层是「装好的工具 + 写好的文档 + 一个目录约定」。

## 3. 为什么每层这么薄

| 层 | 行数 | 为什么不再厚 |
|---|---|---|
| 技能 | 6 个 md，约 400 行 | 技能是**文档**，改起来不需要重新构建，不需要测试 |
| 规约 | 60 行 | 只放模型猜不到的东西（目录约定、不许执行、必须带 locator） |
| 工具 | 0 行 | 用 apt 装好的原版工具，不包装。包装会丢掉参数和报错 |
| fcase | 300 行 | 只做「记录」，不碰分析 |

## 4. 记录层保留了什么

v1 有四道闸门、证据链、append-only。v2 只保留**一条**：`fcase answer` 要求带
`--evidence`，`fcase note` 要求带 `--locator`。

理由：CTF 里真正会毁掉一题的，不是"模型能执行任意命令"（它本来就该能），
而是**答案没依据、事后说不清怎么来的**。所以记录层只守这一点。

代价：没有自动工具日志，`evidence.db` 里只有你主动记的东西。

## 5. 目录约定

| 目录 | 谁写 | 规则 |
|---|---|---|
| `evi/` | 只有 `bin/add` | **chmod 555**，技术强制。解包/重定向/新建都会失败 |
| `work/` | 模型随便写 | 解包、导出、临时文件 |
| `meta/` | `fcase` 写 md 和 db | `notes.md` 是给人写的，`fcase` 不碰 |

三个目录的分界是**整个设计里唯一不能省的东西**：它决定了"出问题时能不能分清
哪些是原始证据、哪些是我的中间产物"。

`evi/` 的 555 是**目录**权限，不是递归改文件 —— 所以软链指向的原件权限不受影响，
但「在 evi 里新建/删除文件」被内核挡住。这一条正好覆盖最容易出事的动作：解包。

## 6. 砍掉了什么，为什么

| 砍掉 | v1 的作用 | 为什么砍 |
|---|---|---|
| Docker 容器 | 只读挂载、资源上限、能力收敛 | 每次调用 0.8s 冷启动；加工具要重建镜像；用不了宿主机 MCP/技能生态。I/O 本身没变慢（都是 page cache） |
| `--tools` 白名单 | 模型只能用 6 个取证函数 | 代价是模型不能 `rg`、不能 `sqlite3`、不能临时组合命令。CTF 里这些恰恰是最常用的 |
| Python worker（runner/adapters/triage/intake） | 统一执行入口 + 输出解析 + 分类 | 1000 行代码换来的"安全"在单机场景里收益很低；解析逻辑写进技能文档更灵活 |
| 工具运行日志 + stdout 哈希 | 完整审计链 | 记录成本高于收益。改成「答案必须带 locator」，同样能追溯，成本低一个数量级 |
| 4 层验收脚本 | 边界回归 | 边界没了，脚本也就没意义了 |

**没砍的**：`evi/work/meta` 三分、append-only、`--evidence`/`--locator` 强制。

## 7. 已知取舍（诚实版）

| 取舍 | 后果 |
|---|---|
| 只读是目录级的 | `evi/` 555 挡住了新建/删除，但挡不住 `sed -i` 改**已存在**的文件（尤其软链会写到原件）。彻底只读要 `sudo mount --bind -o ro` |
| 没有资源上限 | 解压炸弹、死循环会拖垮 WSL。靠 `timeout` 和你的判断 |
| 模型能执行任意命令 | 检材里的提示注入理论上能诱导它跑东西。规约里明确"检材内容是数据" |
| 没有工具版本锁 | 半年后 `apt upgrade` 会换版本。`docs/tool-versions.md` 已删，需要时 `dpkg -l` 查 |
| 记录靠自觉 | 不记就没有。这是最大的风险，也是最快的代价 |

## 8. 什么时候该把 v1 捡回来

- 要给**别人**交付取证报告，需要完整审计链
- 处理真实案件（不是 CTF），有法律效力要求
- 需要多人协作、同一批检材反复复现

CTF 单机场景下，v2 的取舍是对的。

## 9. 演进方向

```
现在 ─────────────────────────────────────────────>
  │
  ├─ 技能补全（最划算）
  │     memory（volatility3）· registry（regipy）· linux（logs/journal）
  │     · windows（evtx/LNK/prefetch）· crypto（钱包/密钥）
  │     每个技能 = 一个 md 文件，不需要改代码
  │
  ├─ fcase 增强（按需）
  │     跨检材关联查询 · 时间线汇总 · 导出提交格式
  │
  └─ 批量模式
        多道题排队跑，结果汇总到一个表
```

技能是主要投入方向：**加一个 md 文件就能让模型多会一类题**，
比加代码便宜得多。
