# 任务：把题目和检材分类成「题组」

你要读 `meta/plan-in.md`（题目清单 + 检材清单），输出 `meta/map.json`。

## 输出格式（严格按这个结构，不要加字段）

```json
[
  {
    "id": "G1",
    "name": "WhatsApp 账号与社群",
    "artifact": "FUNG_CC_mobile.zip",
    "qids": ["Q47", "Q48", "Q49"],
    "depends": [],
    "est_min": 60,
    "reason": "这些题都在查同一份 ChatStorage.sqlite，且 Q48 起为「承上题」"
  }
]
```

字段说明：

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | 是 | `G1`、`G2`… 按执行顺序编号（先易后难、先解锁下游的） |
| `name` | 是 | 人话名字，6–12 字，要能一眼看懂在查什么 |
| `artifact` | 是 | 该组主要依赖的检材文件名（必须与 `evi/` 里的名字完全一致） |
| `qids` | 是 | 题号数组，**必须覆盖全部题目，且每题只出现一次** |
| `depends` | 是 | 依赖的组 id 数组（依赖它的产物，如密码、解出的容器），没有就写 `[]` |
| `est_min` | 是 | 预估分钟数（整数），用于调度排序 |
| `reason` | 否 | 一句话说明为什么这么分，方便人复核 |

## 分类原则

1. **同组 = 同一份中间产物 + 连续的问题链**
   - 「承上题」必须同组
   - 共享同一份数据（同一个 sqlite / 同一个容器 / 同一批照片）的题同组
2. **组大小 2–4 题**（重要）。
   - 组是**并行调度的单位**，组越粗，墙钟越容易被「最长的那一组」卡住。
     实测：20 组时最长单组 25 分钟，直接把总时间锁死在 25 分钟以上。
   - 目标 30–50 组，平均 3 题/组。128 题 → 约 40 组。
   - 「承上题」必须同组，所以依赖链本身是天然的分组边界。
   - 允许 1 题的组，但不要超过总数的 20%。
3. **换检材必换组**。一个组只能绑一个 `artifact`
4. **依赖要标出来**。典型：`Q92–Q98 都要先解开 xcontainer，而解它的密码线索在 Q91`
   → 把「解容器」单独成组，钱包题依赖它
5. **先易后难**：小检材、选择题、理论题排前面；需要深挖的先排后面
6. **理论题单独成组**：完全不依赖检材的题（如"助记词通常由 12–24 个单词组成"）
   组一个 `theory` 组，`artifact` 填该组题目的主要检材，`est_min` 给 1–2 分钟。
   这样调度器会最先做完它
6. **跨检材关联不用建组**，但要在 `reason` 里写一句（例："该组群聊提到 U 盘持有人梁燕玲，与 G20 弱关联"）

## 判断线索

- 题干里的**人名 / 文件名 / 应用名**是最强的分组信号
- 题干里的**「承上题」**表示依赖上一题
- 检材类型决定技能：`ios-dump` → 手机备份；`disk` → 磁盘/镜像；`zip` → 压缩包
- 如果一组题看起来什么都问一点（如"综合题"），单独成组，`est_min` 给大一些

## 自检（写完必须过一遍）

- [ ] 所有题号都出现了，且只出现一次
- [ ] 每个 `artifact` 都在 `evi/` 清单里
- [ ] 没有跨检材的组
- [ ] `depends` 里的组 id 都真实存在，且编号更小
- [ ] 组数在合理范围：**题目数 ÷ 3**，上下浮动 30%（128 题 → 30–55 组）
- [ ] 没有超过 5 题的组

写完后运行 `fcase plan --apply`，它会校验；有错会告诉你哪里不对。
